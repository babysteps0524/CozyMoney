# CozyMoney 회원가입 및 인증 기능 구현 지시서

## 1. 역할과 작업 목표

너는 Astro, TypeScript, Bun, UnoCSS, Cloudflare Pages를 이용한 웹사이트 개발 경험이 풍부한 시니어 풀스택 개발자야.

다음 프로젝트를 분석하고, 기존 아키텍처를 최대한 유지하면서 `cozymoney.kr`에 안전하고 유지보수하기 쉬운 회원가입 및 인증 기능을 구현해.

- GitHub 저장소: [https://github.com/babysteps0524/CozyMoneyCalculator.git]
- 대상 웹사이트: [https://cozymoney.kr/]
- 기본 작업 기준: `main` 브랜치의 최신 코드
- 로컬 프로젝트 경로: `E:\CozyMoneyCalculator`
- 패키지 관리자: Bun
- 배포 환경: Cloudflare Pages
- 주요 기술: Astro, TypeScript, UnoCSS Attributify
- 현재 서비스 성격: 계산기와 생활도구를 제공하는 정적 생성 기반 웹사이트

단순히 회원가입 화면만 만드는 것이 아니라, 실제로 계정을 생성하고 인증하며 안전하게 로그인 상태를 유지할 수 있는 기능을 구현해야 해.

단, 실제 인증 기능을 구현하기 위해 반드시 필요한 경우가 아니라면 기존 코드 구조를 임의로 변경하지 마.

## 2. 반드시 지켜야 하는 Git 브랜치 규칙

### 2.1 `main` 브랜치 직접 수정 금지

다음 규칙을 반드시 지켜.

1. `main` 브랜치에 직접 코드를 수정하거나 커밋하지 마.
2. `main` 브랜치에 직접 푸시하지 마.
3. 기존 작업 내용을 확인한 후 별도의 기능 브랜치를 만들어.
4. 새 브랜치 이름은 다음을 사용해.

   `feature/user-authentication`

5. 해당 브랜치에서만 코드를 수정하고 테스트해.
6. 작업이 완료되더라도 `main`에 병합하지 마.
7. GitHub Pull Request를 자동으로 병합하거나 배포를 실행하지 마.
8. 최종 병합 여부는 내가 직접 결정할 거야.

### 2.2 브랜치 생성 전 확인

먼저 다음을 확인해.

- 현재 Git 브랜치
- 작업 디렉터리의 수정되지 않은 파일
- 미커밋 변경 사항
- 현재 `main`의 최신 커밋
- 원격 저장소와 로컬 저장소의 동기화 상태

기존에 수정 중인 파일이 있다면 덮어쓰거나 삭제하지 마.

작업 중인 변경 사항이 있다면 먼저 상태를 분석하고, 기존 변경 사항을 보존할 수 있는 안전한 방법을 선택해.

브랜치를 생성하기 전에 기존 작업을 무조건 초기화하거나 다음 명령을 사용하지 마.

- `git reset --hard`
- `git clean -fd`
- `git checkout .`
- 그 밖에 기존 변경 사항을 강제로 삭제하는 명령

현재 작업 상태가 불분명하거나 브랜치를 안전하게 생성할 수 없다면 임의로 진행하지 말고 문제를 보고해.

### 3.3 기존 계산기와 생활도구 보호

현재 웹사이트의 핵심 기능은 계산기와 생활도구야.

회원가입 기능을 추가하면서 기존 기능을 손상시키지 마.

- 기존 계산기 계산 로직을 수정하지 마.
- 기존 생활도구 로직을 수정하지 마.
- 기존 페이지 URL을 임의로 변경하지 마.
- 기존 SEO 메타데이터를 불필요하게 변경하지 마.
- 기존 사이트맵 생성 구조를 임의로 변경하지 마.
- 기존 광고 코드와 AdSense 배치 구조를 중복 생성하지 마.
- 기존 GA4 설정을 중복 삽입하지 마.
- 기존 공통 컴포넌트를 이유 없이 새로 만들거나 복제하지 마.

인증 기능과 직접 관련이 없는 파일은 수정하지 않는 것을 원칙으로 해.

불가피하게 다른 파일을 수정해야 한다면, 수정 이유와 영향을 먼저 설명하고 실제 변경 범위를 최소화해.

## 4. 기존 기술 스택과 코드 작성 규칙 유지

### 4.1 기본 기술 스택

다음 기술 스택을 최대한 유지해.

- Astro
- TypeScript
- Bun
- UnoCSS
- UnoCSS Attributify
- Cloudflare Pages
- 기존 정적 생성 기반 페이지 구조

새로운 프레임워크를 도입하기 전에 기존 기술만으로 구현할 수 있는지 먼저 검토해.

특별한 이유 없이 React, Vue, Svelte 등 새로운 UI 프레임워크를 추가하지 마.

기존 프로젝트에 없는 프레임워크나 라이브러리를 무조건 도입하지 마.

### 4.2 일반 CSS 사용 금지

기존 프로젝트의 스타일 작성 원칙을 지켜.

- 일반 `.css` 파일을 새로 만들지 마.
- Astro 파일에 `<style>` 블록을 추가하지 마.
- 기존 UnoCSS Attributify 문법을 우선 사용해.
- 기존 `uno.config.ts`의 색상, shortcut, 테마 설정을 재사용해.
- 기존 공통 버튼과 입력 필드 스타일을 재사용해.
- 기존 다크 모드 동작을 유지해.
- 불필요한 인라인 스타일을 추가하지 마.

예를 들어, 기존에 `cm-input`, `cm-label`, `cm-button-primary`, `cm-button-secondary`, `cm-error`, `cm-help-text`와
같은 shortcut이 정의되어 있다면 실제 정의를 확인한 후 적절하게 재사용해.

위 이름이 실제 설정과 다르거나 수정되었다면 현재 코드의 실제 정의를 기준으로 작성해.

### 4.3 디자인 일관성

회원가입 페이지는 기존 CozyMoney 디자인과 일관되어야 해.

- 기존 헤더와 푸터 재사용
- 기존 콘텐츠 컨테이너 너비 유지
- 기존 글꼴과 색상 토큰 재사용
- 모바일, 태블릿, PC 대응
- 키보드 탐색 지원
- 명확한 입력 오류 표시
- 로딩 및 요청 처리 상태 표시
- 성공 및 실패 메시지 제공
- 버튼의 hover, active, focus 상태 유지
- 다크 모드 대응
- 불필요한 애니메이션 금지
- 불필요한 레이아웃 이동 방지

기존 페이지의 시각적 구조를 크게 변경하지 마.

## 5. 회원가입 기능의 백엔드 아키텍처 결정

이 프로젝트는 정적 생성 기반 Astro 사이트이므로, 회원가입을 구현하려면 브라우저 화면 외에 인증을 처리할 서버 또는 외부 인증 서비스가 필요해.

정적 페이지에 회원가입 폼만 추가하고 실제 인증을 구현한 것처럼 처리하지 마.

### 5.1 가능한 인증 구조 조사

실제 코드와 현재 Cloudflare 배포 환경을 확인한 후 다음 선택지를 비교해.

#### 선택지 A: Cloudflare Pages Functions + D1

검토 항목:

- Astro 정적 페이지와의 호환성
- Cloudflare Pages Functions에서의 인증 처리
- Cloudflare D1 데이터베이스 연결
- 안전한 비밀번호 해시 처리
- 세션 발급 및 검증
- 이메일 인증
- 비밀번호 재설정
- 데이터베이스 마이그레이션
- 배포 설정과 환경 변수
- 운영 및 유지보수 복잡도

#### 선택지 B: Supabase Auth + 데이터베이스

검토 항목:

- 기존 Astro SSG와의 호환성
- 회원가입 및 로그인 지원
- 이메일 인증
- 비밀번호 재설정
- 세션 및 토큰 관리
- 서버 측 권한 검증
- Row Level Security 적용 여부
- 개인정보 접근 통제
- Cloudflare Pages 배포 호환성
- 무료 사용량과 향후 비용
- 공급자 종속성과 이전 가능성

#### 선택지 C: 다른 적합한 인증 서비스

기존 프로젝트에 이미 적절한 인증 서비스가 있다면 우선 검토해.

다른 서비스를 선택할 경우에도 위와 동일한 기준으로 평가해.

### 5.2 아키텍처 선택 원칙

단순히 구현하기 쉽다는 이유만으로 기술을 선택하지 마.

다음 우선순위를 적용해.

1. 보안과 인증의 정확성
2. 기존 Astro SSG 구조와의 호환성
3. Cloudflare Pages 배포 환경과의 호환성
4. 기존 코드 구조를 유지할 수 있는 정도
5. 유지보수와 확장성
6. 구현 복잡도
7. 초기 및 장기 비용
8. 데이터 이전 가능성

실제 호환성이나 가격이 불확실하다면 공식 문서와 최신 정보를 확인해.

지원 여부를 추측해서 작성하지 마.

최종적으로 가장 적합한 방식을 하나 선택하고, 다른 방식보다 적합한 이유를 설명해.

기존 `output: 'static'` 설정은 특별한 근거 없이 변경하지 마. 정적 페이지를 유지하면서 인증용 서버 기능을 별도로 연결할 수 있는지 먼저 검토해.

인증에 서버 기능이 필요하더라도 전체 사이트를 SSR로 전환하는 것을 기본 해결책으로 선택하지 마.

## 6. 구현할 회원 기능

선택한 인증 아키텍처가 지원하는 범위에서 다음 기능을 구현해.

### 6.1 회원가입

회원가입 페이지 경로는 기존 라우팅 규칙을 확인한 뒤 다음 경로를 기준으로 검토해.

`/signup/`

필수 항목:

- 이메일 주소
- 비밀번호
- 비밀번호 확인
- 개인정보처리방침 확인
- 이용약관 확인

실제 서비스에서 법적으로 필요한 동의 항목과 선택 동의 항목은 구분해.

필수 동의와 선택 동의를 하나의 필수 체크박스로 묶지 마.

구현 세부 사항:

- 이메일 형식 검증
- 비밀번호 정책 검증
- 비밀번호 확인 일치 여부 검증
- 필수 동의 여부 검증
- 중복 계정 처리
- 서버 측 입력 검증
- 요청 처리 중 중복 제출 방지
- 명확한 성공 및 실패 메시지
- 요청 실패 시 복구 가능한 UI
- 가입 성공 후 이메일 인증 안내

클라이언트 검증만으로 회원가입을 허용하지 마. 서버에서도 모든 필수 검증을 수행해.

이메일 중복 여부를 확인하는 과정에서 계정 존재 여부가 불필요하게 노출되지 않도록 적절한 응답 정책을 적용해.

### 6.2 로그인

로그인 페이지 경로:

`/login/`

필수 기능:

- 이메일과 비밀번호 입력
- 입력값 검증
- 인증 실패 처리
- 요청 중 로딩 표시
- 로그인 성공 처리
- 안전한 로그인 상태 유지
- 로그아웃 기능과 연결
- 비밀번호 재설정 페이지 연결

로그인 상태를 브라우저의 임의적인 값만으로 판별하지 마.

실제 인증 상태는 선택한 인증 서비스 또는 서버에서 검증할 수 있어야 해.

### 6.3 로그아웃

필수 기능:

- 로그아웃 요청
- 서버 또는 인증 서비스의 세션 무효화
- 클라이언트의 인증 상태 갱신
- 로그아웃 후 비회원 화면 표시
- 로그아웃 실패 시 오류 처리

브라우저 화면에서 로그인 상태만 지우고 실제 세션을 유지하는 방식은 사용하지 마.

### 6.4 이메일 인증

회원가입 후 이메일 소유권을 확인할 수 있도록 이메일 인증 기능을 구현해.

필수 검토 사항:

- 인증 메일 발송
- 인증 링크 또는 인증 코드 검증
- 만료 시간
- 인증 토큰의 안전한 생성과 저장
- 인증 토큰 재사용 방지
- 인증 메일 재발송
- 인증 완료 상태 관리
- 이미 사용한 인증 링크의 처리
- 이메일 발송 실패 처리

인증되지 않은 계정에 어떤 제한을 둘지는 명확하게 정의해.

이메일 인증을 구현할 수 있는 외부 서비스나 환경 변수가 준비되지 않았다면, 구현하지 않은 기능을 완료된 것처럼 표시하지 마.

### 6.5 비밀번호 재설정

비밀번호 재설정 요청 페이지:

`/forgot-password/`

비밀번호 변경 페이지:

`/reset-password/`

필수 기능:

- 이메일을 통한 재설정 요청
- 재설정 링크 또는 토큰 검증
- 토큰 만료 처리
- 토큰 재사용 방지
- 새 비밀번호 검증
- 재설정 성공 및 실패 메시지
- 요청 횟수 제한
- 계정 존재 여부가 과도하게 노출되지 않는 응답

비밀번호 재설정 토큰은 충분히 예측하기 어렵게 생성하고, 사용 후 재사용할 수 없도록 처리해.

### 6.6 마이페이지

마이페이지 경로:

`/account/`

필수 기능:

- 현재 로그인한 계정의 정보 표시
- 이메일 인증 상태 표시
- 비밀번호 재설정 또는 변경 경로 제공
- 로그아웃
- 회원 탈퇴 기능

이메일 등 계정 정보를 변경할 수 있도록 확장할 경우, 변경 전 재인증 등 필요한 보안 절차를 적용해.

다른 회원의 계정 정보가 노출되거나 수정되지 않도록 서버 측에서 권한을 검증해.

### 6.7 회원 탈퇴

회원 탈퇴 기능은 실제 데이터 삭제 또는 계정 비활성화 정책과 일치하도록 구현해.

필수 사항:

- 탈퇴 전 사용자에게 영향 안내
- 탈퇴 의사 재확인
- 요청자 본인 확인
- 서버 측 권한 검증
- 인증 세션 무효화
- 관련 개인정보 처리 정책 반영
- 삭제 또는 보존되는 데이터의 명확한 정의

법적 보존 의무가 있는 데이터가 있다면 실제 적용되는 법률과 서비스 정책을 검토해.

삭제해야 할 데이터와 법적 근거에 따라 보존해야 하는 데이터를 구분해.

회원 탈퇴 버튼을 만들기만 하고 실제 계정 처리가 이루어지지 않는 구현은 허용하지 마.

## 7. 보안 요구사항

보안은 회원가입 기능의 필수 조건이야.

### 7.1 비밀번호

- 비밀번호를 평문으로 저장하지 마.
- 직접 만든 단순 해시 알고리즘을 사용하지 마.
- 검증된 인증 라이브러리 또는 관리형 인증 서비스의 안전한 비밀번호 처리 기능을 우선 사용해.
- 비밀번호를 로그에 출력하지 마.
- 비밀번호를 분석 도구나 광고 도구에 전달하지 마.
- 오류 메시지에 비밀번호나 인증 토큰을 포함하지 마.

### 7.2 세션과 쿠키

선택한 인증 구조에 맞게 안전한 세션 처리를 구현해.

가능하면 서버에서 검증 가능한 세션 구조를 사용하고, 브라우저 저장소에 장기 인증 토큰을 무조건 저장하는 방식은 피해야 해.

쿠키를 사용하는 경우 실제 배포 환경에 맞게 다음 속성을 검토해.

- `HttpOnly`
- `Secure`
- 적절한 `SameSite`
- 적절한 만료 시간
- 세션 만료 및 무효화

`HttpOnly` 쿠키가 필요한 구조라면 클라이언트 JavaScript로 접근 가능한 쿠키에 인증 정보를 저장하지 마.

세션 탈취, CSRF, XSS, 재전송 공격 등 해당 구조에 관련된 위험을 평가해.

### 7.3 서버 측 권한 검증

- 중요한 인증 검증을 브라우저에만 맡기지 마.
- 회원 전용 API는 요청마다 인증과 권한을 확인해.
- 클라이언트가 전달한 회원 ID만 믿고 개인정보를 조회하지 마.
- 비밀번호 재설정 및 회원 탈퇴 요청에 적절한 권한 검증을 적용해.
- 데이터베이스 접근 권한을 최소화해.
- 필요한 경우 데이터베이스 Row Level Security 정책을 적용해.
- 외부 인증 서비스의 비밀 키를 브라우저 코드에 포함하지 마.

### 7.4 요청 보호

구현 구조에 맞게 다음을 검토해.

- 무차별 대입 공격 방지
- 로그인 및 인증 요청 횟수 제한
- 입력값 검증과 정규화
- SQL 인젝션 방지
- CSRF 방지
- 오픈 리디렉션 방지
- 민감 정보 로그 노출 방지
- 이메일 인증 및 비밀번호 재설정 토큰의 만료와 재사용 방지
- 안전한 오류 응답
- 인증 요청의 출처 검증

모든 보안 항목을 무조건 복잡한 자체 구현으로 만들지 마. 기존 플랫폼과 검증된 라이브러리가 제공하는 안전한 기능을 우선 활용해.

### 7.5 비밀 정보 관리

다음 정보는 소스 코드에 직접 입력하지 마.

- 데이터베이스 비밀번호
- 인증 서비스의 비밀 키
- 이메일 서비스 API 키
- 세션 서명 키
- 기타 서버 전용 비밀 정보

실제 환경 변수와 공개 환경 변수의 차이를 확인해.

Astro의 `PUBLIC_` 접두사가 붙은 환경 변수는 클라이언트에 노출될 수 있으므로, 서버 전용 비밀 정보에 사용하지 마.

`.env` 파일에 실제 비밀 키를 넣었다면 Git에 커밋되지 않도록 확인해.

환경 변수 이름과 설정 방법은 실제 구현에 맞게 문서화해.

## 8. 정적 생성과 SEO 유지

기존 사이트는 정적 생성 기반이므로 회원 기능을 추가하더라도 공개 페이지의 SEO와 성능을 최대한 유지해야 해.

### 8.1 기존 정적 페이지 유지

- 공개 계산기 페이지는 기존 정적 생성 방식을 유지해.
- 공개 생활도구 페이지도 기존 생성 방식을 유지해.
- 회원가입 기능 때문에 전체 사이트를 불필요하게 SSR로 전환하지 마.
- 기존 페이지 URL과 canonical URL을 임의로 변경하지 마.
- 인증 기능에 필요한 서버 엔드포인트만 적절하게 추가해.

### 8.2 인증 페이지의 검색 노출

다음 페이지는 검색 엔진에 노출할 필요가 있는지 판단해.

- 회원가입
- 로그인
- 비밀번호 재설정
- 비밀번호 변경
- 이메일 인증
- 마이페이지

일반적으로 개인 계정 화면이나 인증 절차 페이지는 검색 결과에 노출하지 않는 방향으로 검토해.

`noindex` 메타 태그 등을 적용하되, 메타 태그만으로 개인정보 접근을 보호했다고 판단하지 마.

### 8.3 사이트맵

인증 페이지가 기존 사이트맵에 불필요하게 포함되지 않도록 확인해.

- 기존 계산기 URL을 제거하지 마.
- 기존 생활도구 URL을 제거하지 마.
- 공개 페이지의 사이트맵 구조를 불필요하게 변경하지 마.
- 인증 페이지가 포함되는지 실제 빌드 결과를 확인해.
- 빌드 후 사이트맵 검증이 통과하는지 확인해.

## 9. 헤더와 푸터 연결

기존 공통 컴포넌트인 `Header.astro`, `Footer.astro`, `BaseLayout.astro`를 우선 활용해.

### 9.1 비회원 상태

비회원에게 다음 메뉴를 제공하는 방안을 검토해.

- 로그인
- 회원가입

### 9.2 로그인 상태

로그인한 사용자에게 다음 메뉴를 제공하는 방안을 검토해.

- 마이페이지
- 로그아웃

단, 현재 Astro 정적 페이지에서 로그인 상태를 어떻게 안전하게 표시할 수 있는지 먼저 분석해.

정적 HTML 생성 시점에 사용자별 로그인 상태가 고정되어 출력되는 구조를 만들지 마.

필요하다면 공통 헤더에 최소한의 클라이언트 측 상태 갱신을 적용하되, 실제 인증과 권한 검증은 서버 또는 인증 서비스에서 수행해.

인증 상태 확인을 위해 전체 사이트를 불필요하게 무겁게 만들지 마.

기존 헤더의 모바일 메뉴, 접근성, 레이아웃을 유지해.

## 10. 개인정보처리방침 및 이용약관

현재 개인정보처리방침과 이용약관을 반드시 확인해.

회원가입을 도입하면 개인정보 처리 방식이 달라질 수 있으므로 기존 문서를 그대로 두지 마.

### 10.1 개인정보처리방침

실제로 구현한 기능과 수집 항목을 기준으로 필요한 내용을 수정해.

검토할 항목:

- 수집하는 개인정보 항목
- 개인정보 수집 목적
- 필수 및 선택 수집 항목
- 개인정보 보유 및 이용 기간
- 회원 탈퇴 후 처리 방식
- 개인정보 삭제 및 파기
- 개인정보 처리 위탁 여부
- 외부 인증 또는 이메일 서비스 사용 여부
- 개인정보의 국외 이전 여부
- 개인정보 보호 책임 및 문의 방법
- 이용자의 권리와 행사 방법
- 적용되는 법률상 의무

실제로 수집하지 않는 개인정보를 수집한다고 작성하지 마.

실제로 적용되지 않는 보유 기간이나 법적 근거를 임의로 만들지 마.

### 10.2 이용약관

필요한 경우 다음 내용을 검토해.

- 회원 자격
- 계정 관리 책임
- 계정 이용 제한
- 회원 탈퇴
- 서비스 이용 조건
- 서비스 변경 및 종료
- 책임과 분쟁 처리

법적 검토가 필요한 내용은 확정적인 법률 자문인 것처럼 표현하지 말고, 운영자가 확인해야 할 부분을 구분해.

### 10.3 동의 기록

법적으로 또는 운영상 필요한 동의 기록을 어떻게 저장할지 검토해.

- 동의한 약관의 버전
- 동의 시각
- 필수 및 선택 동의의 구분
- 선택 동의 철회 처리

필요한 경우에만 수집하고, 실제 처리 방식과 개인정보처리방침을 일치시켜.

## 11. 이메일 발송 설정

이메일 인증과 비밀번호 재설정에 이메일 발송이 필요하다면 적합한 이메일 서비스를 조사해.

선택한 서비스에 대해 다음을 확인해.

- 현재 아키텍처와의 호환성
- API 지원
- 환경 변수 관리
- 발신 이메일 도메인 인증
- SPF, DKIM 등 필요한 설정
- 이메일 발송 실패 처리
- 무료 사용량과 비용
- 요청 제한
- 테스트 환경과 운영 환경의 분리

이메일 서비스가 아직 연결되지 않았더라도 실제 발송 기능이 작동하는 것처럼 처리하지 마.

운영에 필요한 설정이 없으면 어떤 환경 변수와 DNS 설정이 필요한지 정확하게 안내해.

실제 발송을 검증하지 못했다면 테스트 이메일이 성공적으로 전송되었다고 보고하지 마.

## 12. 데이터베이스와 데이터 모델

선택한 인증 방식에 따라 필요한 데이터 구조를 설계해.

가능한 항목:

- 사용자 계정 식별자
- 이메일 주소
- 이메일 인증 상태
- 계정 생성 시각
- 계정 갱신 시각
- 약관 동의 기록
- 세션 또는 인증 관련 데이터
- 비밀번호 재설정 및 이메일 인증 관련 데이터

관리형 인증 서비스를 선택했다면 해당 서비스가 기본적으로 관리하는 데이터를 불필요하게 중복 저장하지 마.

비밀번호를 직접 저장하는 설계가 불가피하다면 검증된 인증 라이브러리의 권장 구조를 따르고 안전한 비밀번호 해시를 사용해.

### 데이터베이스 변경 규칙

- 기존 테이블과 데이터에 영향을 주는지 확인해.
- 필요한 마이그레이션을 작성해.
- 마이그레이션의 적용 및 롤백 방법을 문서화해.
- 운영 데이터 삭제나 초기화를 수행하지 마.
- 실제 데이터베이스에 임의로 파괴적인 변경을 실행하지 마.
- 개발 환경과 운영 환경을 구분해.
- 비밀 정보나 개인정보를 테스트 로그에 노출하지 마.

## 13. 테스트 작성

회원가입은 보안과 개인정보를 다루므로 테스트를 반드시 작성해.

기존 Bun 테스트 구조와 테스트 명명 규칙을 먼저 확인해.

가능하면 기존 테스트 도구를 재사용하고, 새로운 테스트 프레임워크를 불필요하게 추가하지 마.

### 13.1 회원가입 테스트

- 정상적인 이메일과 비밀번호
- 잘못된 이메일 형식
- 비밀번호 정책 위반
- 비밀번호 확인 불일치
- 필수 동의 누락
- 이미 가입된 이메일
- 중복 요청
- 서버 요청 실패
- 데이터베이스 오류
- 이메일 발송 오류

### 13.2 로그인 테스트

- 정상 로그인
- 잘못된 비밀번호
- 존재하지 않는 계정
- 인증되지 않은 계정의 정책 처리
- 만료된 세션
- 무효화된 세션
- 요청 횟수 제한

### 13.3 이메일 인증 및 비밀번호 재설정 테스트

- 유효한 인증 토큰
- 만료된 토큰
- 이미 사용한 토큰
- 잘못된 토큰
- 재설정 요청의 계정 정보 노출 방지
- 새 비밀번호 정책
- 인증 메일 발송 실패

### 13.4 권한 및 개인정보 보호 테스트

- 로그인하지 않은 사용자의 보호된 API 접근
- 다른 사용자의 계정 정보 조회 시도
- 다른 사용자의 계정 정보 변경 시도
- 다른 사용자의 회원 탈퇴 요청
- 잘못된 리디렉션 URL
- 비밀 정보가 브라우저 코드에 노출되는지
- 인증 페이지에 개인정보가 정적으로 노출되는지

### 13.5 UI 테스트

가능한 범위에서 다음을 확인해.

- 모바일 화면
- 태블릿 화면
- PC 화면
- 키보드 탐색
- 입력 필드 접근성
- 오류 메시지 표시
- 로딩 상태
- 다크 모드
- 로그인 및 로그아웃 후 헤더 상태
- 기존 계산기 및 생활도구 화면 회귀 여부

실행하지 않은 테스트를 통과했다고 보고하지 마.

## 14. 기존 프로젝트 검증 명령

프로젝트의 `package.json`을 먼저 확인하고 기존 검증 명령을 그대로 사용해.

현재 프로젝트에서 다음 명령을 사용하고 있다면 순서대로 실행해.

```bash
bun run check
bun run test
bun run build
bun run verify
```

`bun run verify`가 위 검증을 이미 모두 실행하는 구조라면 중복 실행의 필요성을 판단해. 최종적으로 전체 검증 결과를 확인해야 해.

### 검증 중 오류가 발생한 경우

- 오류 원인을 분석해.
- 회원 기능 변경으로 발생한 오류인지 기존 오류인지 구분해.
- 회원 기능과 직접 관련이 없는 기존 코드를 무분별하게 수정하지 마.
- 오류를 숨기기 위해 테스트를 삭제하거나 비활성화하지 마.
- 타입 오류를 무분별하게 `any`로 처리하지 마.
- 빌드 오류를 임시 우회만 하고 완료로 보고하지 마.

검증이 실패하면 실패한 명령, 주요 오류, 원인, 수정 여부를 보고해.

## 15. Cloudflare Pages 배포와 환경 설정

현재 프로젝트의 Cloudflare Pages 배포 방식을 먼저 조사해.

기존 배포 방식을 임의로 바꾸지 마.

- GitHub 기반 기존 배포 흐름 유지
- GitHub Actions를 새로 도입하지 마.
- 기존 Cloudflare Pages 프로젝트를 임의로 변경하지 마.
- 운영 환경에 자동 배포하지 마.
- 실제 운영 데이터베이스를 임의로 변경하지 마.
- 실제 운영 비밀 키를 코드에 저장하지 마.

회원 기능에 서버 측 처리가 필요하다면, 현재 Cloudflare Pages 환경에서 지원하는 방법을 공식 문서로 확인해.

필요한 설정을 구현한 후 운영자가 직접 설정할 수 있도록 정리해.

예를 들어 실제 선택한 구조에 따라 다음을 안내해.

- 데이터베이스 생성
- 데이터베이스 연결
- 환경 변수 설정
- 서버 전용 비밀 키 설정
- 이메일 발송 서비스 설정
- 필요한 DNS 설정
- 데이터베이스 마이그레이션
- 로컬 테스트
- 미리보기 환경 테스트
- 운영 배포 전 확인 사항

위 항목을 모두 무조건 추가하지 말고 실제로 선택한 아키텍처에 필요한 것만 안내해.

프로젝트에 필요한 설정이 없더라도 임의의 값으로 운영 환경이 작동한다고 가정하지 마.

## 17. 코드 변경 범위 최소화

기존 프로젝트는 이미 계산기와 생활도구를 제공하고 있으므로 불필요한 리팩터링을 하지 마.

- 전체 디렉터리 구조를 임의로 재편성
- 기존 계산기 아키텍처의 무관한 변경
- 기존 생활도구 아키텍처의 무관한 변경
- 공통 컴포넌트의 무분별한 분리 또는 통합
- 기존 디자인 시스템의 전면 교체
- 전체 사이트의 SSR 전환
- 기존 URL의 임의 변경
- 사용 중인 라이브러리의 무분별한 교체
- 테스트를 통과시키기 위한 검증 기준 완화
- 인증 기능과 관계없는 파일의 대량 수정

더 좋은 구조가 필요하다고 판단하면 먼저 현재 구조의 문제점과 개선 이유를 설명해.

실제로 필요한 개선만 적용하고, 그 외의 구조 개선은 별도 제안으로 남겨.

## 18. 완료 조건

다음 조건을 모두 확인해야 작업 완료로 보고할 수 있어.

### 코드와 Git

- [ ] `main` 브랜치를 직접 수정하지 않았다.
- [ ] `feature/user-authentication` 브랜치에서 작업했다.
- [ ] 기존 미커밋 변경 사항을 보존했다.

- [ ] 기존 계산기와 생활도구 로직을 불필요하게 변경하지 않았다.

### 인증

- [ ] 실제 계정 생성이 동작한다.
- [ ] 실제 로그인과 로그아웃이 동작한다.
- [ ] 세션 또는 인증 상태가 안전하게 검증된다.
- [ ] 이메일 인증이 설정된 환경에서 실제로 동작한다.
- [ ] 비밀번호 재설정이 설정된 환경에서 실제로 동작한다.
- [ ] 마이페이지에서 본인 계정만 조회할 수 있다.
- [ ] 회원 탈퇴가 실제 계정 정책에 맞게 처리된다.
- [ ] 서버 측 권한 검증이 적용된다.
- [ ] 민감한 인증 정보가 클라이언트 코드에 노출되지 않는다.

### 기존 사이트

- [ ] Astro 정적 생성 구조를 불필요하게 변경하지 않았다.
- [ ] 기존 공개 페이지 URL을 유지했다.
- [ ] 기존 계산기 기능이 유지된다.
- [ ] 기존 생활도구 기능이 유지된다.
- [ ] 기존 UnoCSS Attributify 스타일 규칙을 유지했다.
- [ ] 인증 페이지가 사이트맵에 불필요하게 노출되지 않는다.
- [ ] 개인정보처리방침과 실제 데이터 처리가 일치한다.

### 검증

- [ ] `bun run check` 통과
- [ ] `bun run test` 통과
- [ ] `bun run build` 통과
- [ ] `bun run verify` 통과

실행하지 않은 항목은 체크하지 마. 외부 서비스 설정이 없어 실제 동작을 확인할 수 없는 항목은 별도로 표시해.

12. 작업 완료 후 `main`에 병합하지 말고 내가 검토할 수 있도록 결과를 보고해.
